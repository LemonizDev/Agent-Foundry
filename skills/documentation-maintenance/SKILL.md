# Documentation and Source-of-Truth Maintenance

## Purpose

Keep project documentation accurate, navigable and proportionate by maintaining one authoritative home for each important fact and linking related material rather than duplicating it.

## Procedure

1. Identify the document taxonomy, index and authority hierarchy before editing.
2. Determine whether the change affects product scope, architecture, implementation, verification, operations, progress or history.
3. Update the canonical document for the affected subject.
4. Update indexes and cross-references when files move or new resources are added.
5. Keep current verified state separate from historical decisions and superseded plans.
6. Distinguish proposed, implemented, tested, reviewed and released states.
7. Add examples only when they clarify actual use; avoid padding and duplicated explanations.
8. Use stable names, consistent metadata and relative links.
9. Validate links, code examples, tables, diagrams and machine-readable metadata.
10. Update changelog for meaningful user-facing or architectural changes.
11. Preserve provenance for extracted or externally sourced material.

## Restrictions

Do not create a second roadmap, duplicate project vision or generic handoff file without a clear reason. Do not silently rewrite history. Do not describe an unimplemented capability as available.

## Completion criteria

A newcomer can find the right document quickly, the documentation agrees with verified implementation, and every important fact has a clear authoritative source.
